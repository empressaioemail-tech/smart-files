# smart-files

Empressa product: Smart Files. Own repo, own database, own serving process.

SmartSite is a consumer. This is not cortex-api. This is not the Texas property-spine store. This is not Hauska substrate.

Do not put a cortex-prod or atoms `DATABASE_URL` in this repo or its deploy env. Files credentials must not reach the atoms database. Atoms / L26 credentials must not reach the files database.

Other products and actors mount this product. They do not merge it into the public spine. Later mounts (city, title, builder, agent, RWA operators) attach the same way. We are not RWA creators. RWA operators bring their own asset representation and mount onto provenance, this file room, and the map.

Infra: Neon `smart-files` / `snowy-bread-83475727`. GCP `smart-files-505619`. Cloud Run service `smart-files` in us-east1. Live probe is `GET /` (GFE intercepts exact `/healthz` on `*.run.app`).

HTTP: `GET /api/smart-files/folders`, `.../folders/:folderId/files`, `.../files/:entityId`, `.../files/:entityId/placements`, `.../blobs/:contentCid`, `.../search`. Writes: `POST /api/smart-files/folders`, `POST .../folders/:folderId/files`, `POST .../folders/:folderId/share`, `GET .../share/:token`. Writes, personas, and share resolution are unchanged: anonymous callers are 401, bearer is the single `SMART_FILES_SERVICE_TOKEN` from Secret Manager. **Reads are gated separately (G-106, defect #3 closed).** A read refuses with 403 -- anonymous or a token scoped to a different tenant alike -- unless the bearer token resolves to a `SMART_FILES_SERVICE_TOKENS` identity holding a grant for the resource's actual `(scopeType, scopeId)`. `SMART_FILES_SERVICE_TOKEN` is deliberately NOT auto-granted read access to every scope; an environment that hasn't configured `SMART_FILES_SERVICE_TOKENS` reads nothing, by design, rather than keeping the old defect as a silent default. See `src/identity.mjs` (`parseServiceIdentities`, `identityAllowsAnyScope`) and `scripts/read_scope_probe.mjs`. `DATABASE_URL` is Secret Manager only. Do not put either token env var in this repo.

QA UI: https://smart-files-app.vercel.app (Vercel project `smart-files-app`, not property-explorer, not cmdcenter). BFF at `/api/files` holds URL + service token only. Personas are QA actors (Joe/Acme, Jane/Acme, Nick/Empressa), not G-11.

Store: `sql/001_foundation.sql` on Neon `snowy-bread-83475727`. Identity is `src/identity.mjs` (last-segment-is-slug). Default `access_policy` is `tenant-private`. Apply and seed read `%USERPROFILE%\\.empressa\\smart-files.database_url` and refuse a cortex-prod host.

Scopes: `jurisdiction`, `tenant`, `site`, `instrument`. All four are readable, behind the caller-scope gate above; write accepts `tenant` and `instrument` only (`WRITABLE_SCOPE_TYPES`). Each scope brings its own scopeId rule to `SCOPE_ID_VALIDATORS` in `src/identity.mjs`, which is the extension point rather than the scope list. `tenant` scopeId is any non-empty string and is not to be tightened; `jurisdiction` is numeric FIPS; `instrument` is `sec_` or `iss_` plus a 26-character Crockford base32 ULID naming a security-master node. `jurisdiction_fips` is denormalised only for `scopeType = jurisdiction`. Tenant writes carry a QA persona; instrument writes name `scopeType` and `scopeId` in the body and are recorded against the `instrument/service` actor.

Round trip: `SMART_FILES_BASE_URL=... SMART_FILES_SERVICE_TOKEN=... node scripts/scope_roundtrip_probe.mjs` exercises the real HTTP routes for the instrument scope and for every live tenant slug, and exits non-zero on any failure. It authenticates as a single blanket-grant identity (`SMART_FILES_SERVICE_TOKENS` "*"/"*"), which is a legitimate disposable CI/backend identity, not evidence that reads are unscoped. `scripts/read_scope_probe.mjs` is the read-scope-specific probe: it proves anonymous and wrong-tenant-token reads of a folder, file, blob, and placement all refuse with 403 while a matching-tenant token succeeds. CI runs both against a throwaway Postgres on every pull request.

**Submittal uploads (G-107).** `POST .../folders/:folderId/files` accepts two additional, optional body fields. `docSlug`: an explicit, caller-chosen slug (validated against the same alphabet as any docSlug) instead of the default title-derived-plus-counter one. Uploading a SECOND time with the identical `docSlug` is a new VERSION of the SAME document (`currentVersion` increments, `entityId` is unchanged, response carries `revision: true`) rather than a counter-suffixed sibling document -- this is what makes a submittal's identity stable across revisions. `provenance`: an object with five required keys (`capturedBy`, `capturedAt` as ISO-8601, `sourceKind` from the closed set `staff-upload`/`applicant-upload`/`feed`/`instrument-write`, `originalFilename`, `declaredRole`) validated by `identity.mjs`'s `validateProvenance` -- a missing or invalid key refuses the write (400) rather than defaulting. Neither field is required: a caller that omits both keeps exactly the pre-existing behavior (title-derived slug, `{sourceLabel, uploadedBy}` provenance), so no existing integration is broken by this addition. `scripts/submittal_upload_probe.mjs` proves both properties (stable-slug-is-a-revision, missing-provenance-key-refuses) against real HTTP routes; wired into CI alongside the other two probes.

**Real content search (search wave, `doc_repo/_decisions/2026-09-04_smart_files_search_wave_scope.md`).** `POST .../folders/:folderId/files` extracts text SYNCHRONOUSLY on upload, gated on `content_type = 'application/pdf'` -- every other content type (including the real bastrop_tx meeting records, which are `application/json`) is never attempted: no job queue exists in this repo and this wave doesn't invent one. Extraction uses `pdf-parse@1.1.4` (the last pre-rewrite release; the current `2.x` line depends on `pdfjs-dist` plus a native-binary canvas package this dependency-light repo has no reason to carry). Extraction failure -- a corrupt PDF, a scanned/image-only PDF with no text layer -- fails ONLY the search index for that version, never the upload: the upload response always carries `searchIndexed` (boolean) and `searchIndexReason` (`null` on success, otherwise a named reason: `content-type-not-indexable` or `no-text-layer` or `extraction-failed: ...`), so nothing is silently pretended to work. See `src/extract.mjs`.

Extracted text lives on `smart_file_versions.search_text` (`sql/005_search_index.sql`) with a `search_tsv` STORED generated `tsvector` column and a GIN index -- generated, not trigger-maintained, so the index can never drift out of sync with `search_text`, and `search_text IS NULL` (never `''`) is the one honest "not indexed" value. `GET /api/smart-files/search?scopeType=&scopeId=&q=` follows the exact `folders` route pattern: scope is resolved and validated, then `requireReadScope` runs BEFORE any data is touched -- the search gate is exactly as strict as every other read route, proven the same way `read_scope_probe.mjs` proves it for the rest. Only the CURRENT version of a document is searched. Results carry `entityId`/`title`/`snippet`/`rank` metadata only, never blob bytes -- those stay behind the separately-gated `/blobs/:contentCid` route. `scripts/search_probe.mjs` proves: a PDF upload is indexed and found by real word content; the real `application/json` shape is never attempted and never appears in results; the access-control gate; and that a missing/trivial `q` refuses (400).

**Placement target (fixes the municode meeting-upload bug).** Every `uploadFileToFolder` write used to hard-code a `'folder'` placement, even when the real target was already knowable -- e.g. smartcity-dashboards' municode calendar scraper uploads a meeting's documents with no way to say which meeting. `POST .../folders/:folderId/files` now optionally accepts `targetType`/`targetId` (travel together; `targetType` is validated against the same value set as the `smart_file_placements` CHECK constraint, in `store.mjs`'s `PLACEMENT_TARGET_TYPES`). When given, the placement is written with THAT `target_type`/`target_id` instead of `folder`; when omitted, behavior is byte-for-byte unchanged (a single `folder` placement at `folderId`) -- no existing caller, including the municode scraper as it calls this API today, is affected. `scripts/placement_target_probe.mjs` proves both the default and explicit-target paths, plus the validation refusals. Wiring `smartcity-dashboards`' municode scraper to actually pass `targetType: 'meeting'` is a separate, follow-on change in that repo -- not done here.
